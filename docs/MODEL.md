# Модель риска оттока и денежная оценка

## Что оцениваем

Оцениваются только **действующие услуги**: `active`, `suspended`, `prolong_wait`, созданные не позже опорной даты. Услуги в статусах `deleted` и `blocked` уже потеряны: они не получают score, но учитываются как история клиента и как факт оттока на графике.

Если у клиента нет действующих услуг, оценки нет: `score = null`, уровень `none`, причина указана явно, как требует ТЗ.

## Score

Модель — прозрачная скоринговая карта. У каждого признака есть значение от 0 до 1 и вес в баллах. Веса редактируются в панели.

```
score услуги   = min(100, Σ вес × значение)
score клиента  = максимум по его услугам   (или средневзвешенное по выручке: aggregation = revenue_weighted)
вероятность ухода клиента = score клиента / 100
лояльность     = 100 − score
уровень        = high, если score ≥ 60; medium, если ≥ 30; иначе low   (пороги настраиваются)
```

| Признак | Вес | Значение 0..1 | Почему это сигнал |
|---|---|---|---|
| `prolong_wait` Ожидает оплаты | 45 | 1, если статус prolong_wait | Срок истёк, через 5 дней услуга удалится |
| `expiring_no_autoprolong` Истекает без автопродления | 30 | 1 − дней до конца / горизонт | Клиенту надо самому вспомнить и заплатить |
| `insufficient_funds` Не хватает средств | 35 | 1 − 0.5 × (дней до первого продления этой услуги, которое уже нечем оплатить) / горизонт; от 1 (платить сейчас) до 0.5 (в конце горизонта) | Когда деньги кончатся, автопродление не сработает, почасовая услуга остановится |
| `churn_history` Уже уходил | 15 | доля удалённых или заблокированных услуг клиента | Прошлое поведение предсказывает будущее |
| `suspended` Сервер выключен | 10 | 1, если suspended | Платит, но не пользуется |
| `unpaid_transactions` Неоплаченные платежи | 10 | доля not_performed транзакций по услуге | Заказ создан, но не оплачен |
| `new_service` Новая услуга | 5 | 1 − возраст / 30 дн. | В первые недели отказываются чаще |

Средства на продления: `balance` плюс `bonusBalance`, если `bonusState = unlocked` (автопродление списывает и бонусы). Продления всех услуг клиента оплачиваются по порядку наступления, наступившие в один момент — по очереди (по id услуги), пока на очередное хватает денег; момент, когда очередное продление уже нечем оплатить, — это «деньги кончатся через N дней». В тексте причины баланс и бонусы указываются отдельно.

Причины клиента: для каждого признака берётся самый сильный вклад среди его услуг, причины сортируются по баллам. Панель показывает текст причины, баллы и услугу.

## Денежная оценка

`price` — цена одного периода `paymentTerm`. Горизонт H = 30 дней (настраивается).

```
продлений в горизонте = сколько раз услугу надо оплатить за H дней (prolong_wait — сразу)
horizonRevenue        = price × продлений
securedByBalance      = часть horizonRevenue, которую автопродление спишет с основного баланса
coveredByBonus        = часть, которую автопродление затем оплатит доступными бонусами
atRisk                = horizonRevenue − securedByBalance − coveredByBonus
expectedLoss клиента  = score клиента / 100 × atRisk клиента        ← главная цифра (сумма по клиентам)
expectedMonthlyLoss   = score клиента / 100 × выручка клиента в месяц
```

Как формула учитывает три фактора из ТЗ:
- **стоимость услуг**: через `horizonRevenue`;
- **балансы**: дважды. Чем раньше кончатся деньги, тем выше риск, а продления, которые автопродление спишет с баланса или бонусов, не попадают в сумму под угрозой. Услуга в `prolong_wait` не покрыта даже при автопродлении: сам статус значит, что автосписание не прошло;
- **риск**: вероятность ухода умножается на сумму под угрозой.

Вероятность ухода берётся у клиента целиком: уходя, клиент уходит со всеми услугами. Поэтому на панели score × сумма под угрозой = ожидаемая потеря. Бонусы — не выручка реальными деньгами, поэтому показываются отдельно от `securedByBalance`. Для клиентов с высоким риском отдельно показываются их балансы и сумма, доступная к выводу (`withdrawBalance`).

Замечание о данных: почасовая услуга за 0,95 € в час — это около 684 € в месяц. Поэтому на исходном наборе организаторов почасовые услуги дают основную часть суммы.

## Опорная дата

Данные — снимок, поэтому «сейчас» определяется настройкой `asOfMode`:
- `snapshot` (по умолчанию): `referenceDate` из снимка, а если её нет, самая поздняя дата в данных;
- `now`: текущее время;
- `fixed`: дата из `asOfFixed`.

## Как добавить признак

Написать функцию в `app/risk/features.py`:

```python
# app/risk/features.py; в импорты файла добавить: from app.risk.terms import monthly_price
@feature("low_replenishment", title="Мало пополняет", default_weight=10,
         description="За всё время пополнил меньше, чем стоит его услуга за год.")
def low_replenishment(ctx: ServiceContext) -> FeatureResult:
    yearly = monthly_price(ctx.service.price, ctx.service.payment_term) * 12
    if yearly == 0 or ctx.account.total_replenished >= yearly:
        return NO_SIGNAL
    return FeatureResult(1 - ctx.account.total_replenished / yearly,
                         f"Пополнил {eur(ctx.account.total_replenished)} — меньше годовой стоимости услуги")
```

Больше ничего менять не нужно. Вес появится в `GET /api/v1/model/settings`, его можно менять через PATCH, вклад и причина попадут в оценки. Миграция не нужна: настройки хранятся в JSONB, а веса новых признаков берутся по умолчанию.

## График оттока

`get_churn_timeline`:
- **факт**: переходы услуг в `deleted` между загруженными снимками. Для удалённых услуг без истории дата оценивается как `expiresAt` + 5 дней и выводится отдельно (`estimatedDeletions`);
- **прогноз**: в день ближайшего списания каждой действующей услуги добавляется её вероятность непродления (score услуги / 100).
